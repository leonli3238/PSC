## Slide 1：本次汇报要回答的三个问题

1. **PSC 的节点 LLM 会不会算错，算错会不会破坏隐私？**（A1）
2. **CertiCount 把计算挪回代码后，端到端能否保持精度且不调用节点 LLM？**（A2）
3. **由 LLM 设计计数程序，设计得对不对、证书靠不靠谱？**（A3 / A4）

**一句话结论：** CertiCount 已经解决“LLM 算错导致隐私越界”；但实验暴露了一个新问题——**LLM 设计的程序可能通过全部检查，却在含噪输入上统计失效**。下一步要补“含噪效用门”。

## Slide 4：A1 结果②——错误转化为可确认的隐私越界

**先定义“越界”：** 相邻图 `x` / `x2` 只差一条边，真实度数只差 **1**；机制发布“模型答案 + Lap(1/2)”。如果模型在两张图上的答案分布可以被区分到 **ε > 2**，就是越界。**答错本身不一定泄露；相邻输入上的“错法不一致”才泄露。** 具体样本见 Slide 4b。

| 模型 | 集合 | 测试对数 | 确认越界 | ε_lb max | 最大计数偏差 |
|---|---|---:|---:|---:|---:|
| 8B 非思考 | main_div | 40 | 24 | 4.19 | 406 |
| 8B 非思考 | nodes | 20 | 15 | **4.30** | 332 |
| 8B 非思考 | random | 60 | 4 | 3.51 | 41 |
| 1.7B | main / main_div / nodes | 40 / 40 / 36 | 38 / 38 / 31 | 4.21 | 449 |
| **program 对照** | main_div + nodes | 60 | **0** | 1.47 | 1 |

- 联合 Bonferroni（M=334，family α=0.05）：**163/334 确认越界**；8B 单独 **49/158**。
- ε_lb 最高 **4.30**，是名义 ε₃=2.0 的 **2.15 倍**。
- program 模式 **0/60**，计数偏差最大仅 1（来自相邻输入本身）。

**边界：** 审计只能证伪；program 的 0/60 表示“未发现越界”，不是隐私证明。

## Slide 4b：四个真实越界样本——模型到底输出了什么

全部来自 `confirm_nodes` 的真实节点对（PM，`source=real`）；两张图只差一条边，下面是模型原始答案（520 次重复，未加机制噪声）。

| 节点 | 真实度 x→x2 | 模型输出 x（520 次） | 模型输出 x2（520 次） | 真实变化 | 模型变化 | ε_lb |
|---|---|---|---:|---:|---:|---:|
| n3 | 38 → 39 | **38（520/520）** | **40（278）、43（190）、42、39** | +1 | **+2 到 +5** | **2.64** |
| n8 | 75 → 74 | **93（222）、90（205）、94、95** | **70（520/520）** | −1 | **−20 到 −25** | **4.26** |
| n37 | 63 → 64 | **43（492）、70（28）** | **90（372）、80（101）、70、73** | +1 | **+27 到 +47** | **4.14** |
| n14 | 237 → 236 | **122（170）、127（151）、128、123、120** | **198（329）、452（95）、210、195、200** | −1 | **+67 到 +332** | **4.30** |

**分析：**

1. **不是“偏差”问题，而是“不稳定性”问题。** n14 在 x 上稳定错到 127（真实 237），如果 x2 也稳定错到 127，机制仍近似 2-DP；但 x2 跳到 198/452，两个分布被拉开，才有 ε_lb=4.30。
2. **一条边的增删会改变模型的计数策略。** n8 真实删 1 条边，模型从 90–95 掉到 70（方向相反、幅度 20–25）；n37 真实加 1 条边，模型从 43 跳到 70–90。
3. **GS=1、噪声尺度 0.5，遮不住 20–300 的跳变。** 单次看只是“答错了”；500 次重复才能看出两个分布的系统性差异。
4. **高度数节点最危险。** 列表越长，模型越容易受顺序/位置影响；PM 的最大度 237 正好落在最不稳定的区间。

## Slide 7b：A3 的任务与真实 prompt/输出

**七个任务：** degree / 2-star / 3-star / triangle（库内）；4-star / 5-star / degree-moment2（库外）。

**LLM 实际输入（5-star，节选）：**

```text
System: You are the curator agent ... You never see the graph. You write the program
that every node runs locally on its own neighbor list; the system derives the program's
sensitivity and the node executes it.

User: The program language:
- P: this node's true neighbors (private and exact)
- N(x): public neighbor set in the noisy graph (misses real edges, contains fake ones)
- D: public degree threshold; size/project/comb/sum/& ...
Smaller sensitivity means less noise: bound degrees with project(P, D) before nonlinear functions.
...
Analyst question: "For each node, the number of 5-stars ... C(degree(node), 5).
Q: What is the total number of 5-stars in the graph?"
The graph has 453 nodes.
Reply with: ```dsl <program>``` + aggregate: <expression over total and n>
```

**LLM 输出（5-star，accepted，9/9 精确）：**

```dsl
count = comb(size(project(P, D)), 5)
return count
```
aggregate: total

**同一骨架下的两种失败（详见文档 4.0.4 / 4.0.5）：**

- **degree design 0**：把 aggregate 硬编码成 `total / 453`，在小测试图上被 453/5 倍缩放错误；反馈只说“under-counts on every failing graph”，模型改局部程序而不是改 aggregate，3 轮后落到 `N(self)`，被拒。
- **triangle**：5/6 接受设计写成 `project(N(self), D)` + 交集，真实运行 334,918 vs 真值 3,284（**RE 100.9**）；唯一正确写法用 `P & N(v)`，RE 1.43。

> 这说明：prompt 里“`N(x)` 是含噪的”这句话不够；模型需要显式的“`N(self)` 不可用于计数”+ 含噪效用门。

## Slide 7c：为什么会写错？

**两类错误，五个机制：**

| 错误 | 模型原话 | 机制 |
|---|---|---|
| `total / 453` | *"Since n is 453, the aggregate is total / 453."* | 把具体实例当程序常量；不知道测试图 n=5/6 |
| 退到 `N(self)` | *"the previous attempt was rejected, which suggests that the program can't access P directly."* | 把 curator 的 "never see the graph" 过度推广到 node |
| 用 `N(self)` 计数 | *"the program must include reading N(self) to consume the budget."* | 把已发布含噪行当成“自己的真实列表” |
| 验算通过 | *"dividing by 2 gives the correct number of edges ... dividing by 3 gives the correct total."* | 在精确图上做符号验算，没模拟 RR 假边 |
| 被接受 | `N(self)=P` in utility test | 检查器看不到真实运行中的 ≈120 条假边 |

**为什么 5-star 没写错、triangle 错 5/6？**

- 5-star 有强模板 `comb(size(project(P,D)),k)`，prompt 也明确提示投影；9/9 命中。
- triangle 没有模板，需要 `P & N(v)` 组合；模型的默认模式退到 `N`，而精确 utility test 对两种写法都放行，没有选择压力。

> 不是“不会数”，而是 **角色/变量语义 + 最小灵敏度代理目标 + 检查器盲区** 共同导致的“符号正确、统计错误”局部最优。

## Slide 9：A3 结果③——核心发现：`N(self)` 捷径

**9 个灾难设计全部使用 `N(self)` 计数；52 个非灾难设计全部使用 `P` / `project(P, D)`。完全分离。**

```text
deg = size(N(self)); return comb(deg, 2)            # 2-star
neighbors = project(N(self), D)
return sum(size(N(v) & neighbors) for v in neighbors) / 2   # triangle
```

| 任务 | 真值 | `N(self)` 程序估计 | 放大倍数 |
|---|---:|---:|---:|
| 2-star | 79,173 | 3,588,147 | 45× |
| 3-star | 3,352,172 | ≈1.47e8 | 44× |
| 4-star | 153,983,040 | ≈4.8e9 | 31× |
| triangle | 3,284 | 334,918 | **102×** |

**机制：**
- `N(self)` 是随机响应发布后的**含噪邻接行**，不是真实邻居。
- ε₁=1 时，PM 每个节点平均混入 **≈120 条假边**，而真实平均度只有 8.94。
- `comb` / 求交是非线性的，假边被平方级放大。
- 模型选择它的原因：读取已发布数据是后处理，**GS=0、无需加噪**——模型在思考过程中明确把“灵敏度最小”当成了目标。

## Slide 10：为什么这些程序通过了所有检查？

| 检查 | 对 `N(self)` 程序的结果 | 原因 |
|---|---|---|
| 灵敏度证书 | 通过（GS=0，且确实正确） | 后处理不消耗隐私 |
| 证伪器 | 通过 | 没有越界 |
| 语义/效用测试 | **通过** | 测试用**真实邻接表**执行，`N(self)=P` |
| 端到端真实运行 | **RE 30–100×** | 真实运行中 `N(self)` 含 ≈120 条假边 |

**结论：**
- **隐私层面没有问题**：A4 在 119 份草稿上 `certificate_unsound = 0`。
- **缺的是统计效用层面的检查**：现在的测试验证“语义是否正确”，不验证“在含噪输入上是否有用”。

> 认证保证了隐私，但没有保证结果有用。

## Slide 11：A4——认证消融：不做认证会怎样

**草稿漏斗（119 份）：**

| 阶段 | 数量 | 占比 |
|---|---:|---:|
| 语法/类型错误（parse） | 34 | 28.6% |
| GS 过松（gs_loose） | 16 | 13.4% |
| 语义错误 | 8 | 6.7% |
| 被证伪器推翻 | 0 | 0% |
| **接受** | **61** | **51.3%** |

**soundness：**
- `certificate_unsound = 0`：没有任何草稿的实测最大变化超过系统自己推导的 GS。
- 反事实：若跳过认证、按任务参考 GS 加噪，**21/85（24.7%）** 可运行草稿会越界，最高 3.33×。
- 被接受程序中，3 个 `size(P)²` 的 GS 比参考界松 **47.6×**，隐私安全但 RE 变为 **2.4×**；现有 loose 检查只覆盖 `comb`，没覆盖乘积。

**一个具体反事实 witness（2-star）：**

```text
name = comb(size(P), 2); return name; aggregate: total
```

- n=7、dmax=4；证伪器找到私有集 `P=[1,2,3,4,5]`（节点 6），两张相邻图的最大输出差 **Δ=5**。
- 2-star 参考 GS=3 → Δ/GS_ref = **1.67×**。
- 该程序自己的推导 GS=**5**，CertiCount 会按 5 加噪，**实际不会泄露**；设计循环把它标为 `gs_loose` 并退回。
- 所以这里的“越界”是“如果按参考界 3 加噪”的反事实，**不是观测到的泄露**。真正观测到的越界在 A1（Slide 4b）。

**口径提醒：**
- 证伪器在 n=5/7 的小图上运行，比值是下界。
- 4/5-star 出现 `inf` 是 D<k 的检查口径问题，不代表真实图上无限泄露。
- 这是反事实分析，不能写成“观测到 PSC 泄露”。

## Slide 12：thinking curator——CoT 没有解决设计问题

- A3 全部 119 次设计调用都是 thinking：平均 **3,950 输出 token/次**，最大 9,151，总设计时间约 **99 分钟**。
- **9 个 `N(self)` 灾难全部由 thinking curator 写出**。
- thinking 在节点执行上有效（Slide 5），但在设计上不是充分条件：CoT 会更好地优化“降低灵敏度”这个目标，但不会自动意识到输入是含噪数据。
- 缺口：没有非思考 curator 的对照，因此无法量化 thinking 对设计质量的贡献。

**成本对比：** 设计是一次性、可缓存的（约 47 万输出 token，按 $0.5/M 约 $0.24）；节点调用为 0。PSC 的节点调用是 O(n)。

## 附：可能被问到的问题

**Q1：thinking 已经 0/20，PSC 不就够了吗？**  
0/20 只覆盖 20 个选定的难节点对，不是保证；>120 度仍有 10.8% 错误，且出现过 1.02e8 的灾难输出。thinking 的节点成本也更高。CertiCount 的目标是“无论模型行为如何，隐私都成立”。

**Q2：9 个灾难只是模型写错了，和方法有什么关系？**  
它们通过了认证、语义测试和证伪器并被系统接受，说明当前的接受门不完整。隐私门是对的，缺的是效用门。

**Q3：A4 的 3.33× 是真实泄露吗？**  
不是。它是“跳过认证、按参考 GS 加噪”的反事实下界。系统实际使用程序自己的 GS，0 unsound。

**Q4：为什么 5-star 比 2-star 更稳？**  
5-star 的模型输出模式高度一致（`comb(size(project(P,D)),5)`），没有出现 `N(self)` 捷径。2-star 的灾难不是能力不足，而是 2 个设计走了捷径；样本只有 10 个，差异不显著。

**Q5：只在 PM 上做，结论能推广吗？**  
目前不能。PM 是重尾图，最适合暴露节点错误；跨图泛化需要 CU / Do 的补充实验。GLM-5.2 在 CU/Do 上的 triangle 也出现了不稳定，说明设计质量问题不是 Qwen 特有。
